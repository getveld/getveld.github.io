Decision from this fixture: block

The rollback ran. The old application check still failed.

This page walks through one synthetic PostgreSQL fixture. The rollback SQL completed, the row count and index checks passed, and the declared generation value returned to its earlier value. A separate SQL read proxy for previous-application behavior then returned 99 instead of the expected 7.

Execution boundary: the proxy ran SELECT legacy_value FROM r3_items WHERE id = 1. No application binary was executed; application startup and write behavior remain untested.

That result is evidence about this fixture and these declared checks. It is not a production-safety claim, a compatibility guarantee, or evidence of buyer demand.

01 · Scenario

A deliberately small compatibility failure

The fixture starts with one row. The prior application expects legacy_value = 7 and generation = 1. The forward migration changes the generation to 2. The synthetic rollback returns the generation to 1 but also changes the legacy value to 99.

Starting state

CREATE TABLE r3_items (
  id integer PRIMARY KEY,
  legacy_value integer,
  generation integer
);
INSERT INTO r3_items VALUES (1, 7, 1);

Forward migration

UPDATE r3_items
SET generation = 2;

Rollback under review

UPDATE r3_items
SET generation = 1;

UPDATE r3_items
SET legacy_value = 99;

02 · Sequence

What actually ran

  1. Establish old state. Create the table and index, insert the synthetic row, and verify the declared SQL read proxy returns 7.
  2. Apply the forward SQL. Verify the new generation is 2, the same SQL read proxy still returns 7, and the row-count invariant remains 1.
  3. Execute the rollback SQL. The database accepts both rollback statements without an execution error.
  4. Run post-rollback checks. The generation, row count, and index checks pass. The SQL read proxy fails because it returns 99 instead of 7. This is not evidence that an application binary started or completed a workflow.
  5. Restore the disposable snapshot. Cleanup returns the fixture to its initial value. Snapshot cleanup is not counted as evidence that the rollback itself was compatible.

Advisory disposition

Block on the declared compatibility failure

The receipt's stage label is post-rollback-old-binary-startup, but the observed check was only the declared SQL read proxy. It records a material failure for that proxy; it does not establish that an application binary was launched or that startup or write workflows were exercised.

04 · Evidence limits

What this did—and did not—prove

What the example demonstrated

  • The listed SQL ran against a disposable PostgreSQL database.
  • The rollback statements completed without a database execution error.
  • The declared post-rollback SQL read proxy returned a value different from its expected value.
  • The receipt kept the skipped forward-index check visible rather than treating it as a pass.

What remains unproven

  • Application binary startup, application write behavior, end-to-end workflow behavior, or broader previous-version compatibility.
  • Production safety, zero data loss, complete compatibility, or release approval.
  • Fresh hidden-holdout generalization or a complete manifest acceptance.
  • Coverage for other PostgreSQL versions, tools, schemas, extensions, or topologies.
  • Observed customer outcomes, buyer demand, willingness to pay, or remediation success.
  • Any check not listed in the evidence packet.
